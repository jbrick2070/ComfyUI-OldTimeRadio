VERDICT: yes-with-fixes. The overall vision is solid, but the pycairo dependency model and surface memory mappings must be isolated to prevent stack-wide installation and runtime failures.

MUST-FIX BEFORE BUILD:
1. [DECISIONS TO HARDEN - 2] The plan proposes adding pycairo as a hard dependency to requirements.video.txt. Because pycairo binds to the system-level C cairo library, installing it via pip will fail on non-Windows platforms (like Linux or macOS) if libcairo2-dev and pkg-config are not pre-installed. [ASSUMPTION] This is assumed to break dependency installation for users running other video engines on clean Linux/macOS environments. Fix: Keep pycairo as an optional, lazy-loaded dependency; do not add it to requirements.video.txt. Validate its importability inside assert_usable, raising a descriptive EngineUnusable exception instructing the user to install pycairo if the engine is selected.
2. [DECISIONS TO HARDEN - 1] Upgrading the existing viz_mxc_cpu engine to use pycairo in place removes the zero-dependency PIL fallback floor. If pycairo fails to load on a user's system, it will fail assert_usable loud and crash the entire render pipeline since there is no fallback engine. Fix: Keep the existing PIL-based viz_mxc_cpu intact. Ship the new cairo visualizer as a separate engine (e.g. viz_mxc_mandala). In the new engine, set fallback_engine = "viz_mxc_cpu" so the pipeline gracefully degrades to the zero-dependency PIL visualizer if pycairo is missing.
3. [OPEN QUESTIONS FOR THE PANEL - 5] The prototype's surface_to_rgb method maps surface bytes directly to numpy using np.ndarray(shape=(h, w, 4), buffer=surface.get_data()), assuming the stride is exactly w * 4. However, Cairo aligns row strides to 16/64-byte boundaries. If a user requests a custom width that is not a multiple of Cairo's alignment, the stride will exceed w * 4, causing horizontal image skewing, tearing, or out-of-bounds memory access. Fix: Retrieve the actual stride via surface.get_stride() and pass it explicitly to the numpy array constructor via strides=(surface.get_stride(), 4, 1).

SHOULD-FIX:
1. [DECISIONS TO HARDEN - 6] Reusing scope_draw.build_scanlines and build_vignette over cairo output via a PIL roundtrip (converting Cairo to PIL, to numpy for vignette multiplication, back to PIL, then to numpy for noise) introduces a severe CPU processing bottleneck for 1472x832 frames. Fix: Implement the scanline overlay and radial vignette multiply directly in Cairo using native cairo.RadialGradient, patterns, and cairo.OPERATOR_MULTIPLY, leaving only the film grain noise to be applied via numpy on the final extracted buffer.
2. [DECISIONS TO HARDEN - 3] The prototype's paint_mandala concentric rings and spoke outer bounds scale up to 0.54 * min(w, h) and 0.57 * min(w, h). On a 16:9 canvas (1472x832), this exceeds the 416px vertical center boundary (0.50 * h), causing the mandala's top and bottom edges to clip off the screen. Fix: Scale down the radius multiplier factors in paint_mandala (e.g. keep maximum outer bounds below 0.45 * min(w, h)) so the mandala remains fully bounded on a 16:9 screen.
3. [OPEN QUESTIONS FOR THE PANEL - 4] Reusing a single cairo.Context across frames without saving/restoring state allows transformations, line widths, and clipping paths to accumulate and leak between frame draws. Fix: Instantiate a fresh cairo.Context(surface) per frame or wrap paint_mandala's drawing body in ctx.save() / ctx.restore().
4. [DECISIONS TO HARDEN - 7] The capabilities registration for the new engine is not defined in the plan, which will break test_capability_profiles.py if a new row is not added. Fix: Explicitly define a new CAPABILITIES row in registry.py: "viz_mxc_mandala": {"vram_class": "cpu", "vram_estimate_mb": 0, "required_toolchain": None, "requires_sidecar": False, "cpu_ok": True, "model_requirements": []}.

OPTIONAL / NICE-TO-HAVE:
1. [FUTURE MODES] Future visual looks (Spectral Voice Entities, static portals) should strictly be registered as independent engines to conform to the "one grammar per engine" architectural constraint.

CUT THESE (scope / over-engineering):
1. [DECISIONS TO HARDEN - 5] Caching static layers (bg gradient, scanline/vignette overlays) across frames. Scanlines and vignette must sit *above* reactive elements to maintain the CRT look, preventing pre-composition with the background. Additionally, cairo.RadialGradient is extremely fast to paint, and the overlay arrays are already generated once per render run rather than per frame. Caching them provides no performance benefit and complicates the drawing pipeline.
