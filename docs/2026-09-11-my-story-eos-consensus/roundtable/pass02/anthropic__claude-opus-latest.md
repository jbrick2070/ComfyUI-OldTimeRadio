# MUST-FIX BEFORE BUILD

1. **[_otr_model_loader.make_generate_fn / make_polish_generate_fn, diff @2542 and @2727]** The fail-on-output-limit guard is now `len(generated_ids) >= effective_max_new_tokens and int(generated_ids[-1]) not in prepared["eos_token_ids"]`. If `effective_max_new_tokens` is 0 or the backend returns a prompt-length-only sequence, `len(generated_ids) == 0 >= 0` is True and `generated_ids[-1]` raises `IndexError` from inside a supposedly-fail-closed branch — turning a truthful capacity failure into an opaque exception. The constrained path at :383 already guards this correctly (`bool(len(generated_ids)) and ...`). Fix: mirror it — `and (not len(generated_ids) or int(generated_ids[-1]) not in prepared["eos_token_ids"])`. This is the *same* class of eager-last-token defect the earlier full suite already caught once on the base path; it was fixed at the writer/inspect boundary but the base/polish raise still indexes unconditionally. [ASSUMPTION] that `generated_ids` can be length-0 here; verify: whether any caller can reach these factories with `effective_max_new_tokens <= 0` after budget normalization.

2. **[writer @956, constrained @337, loader @2485/@2685]** `eos_token_id=prepared["eos_token_ids"] or None` is ambiguous and route-dependent. Passing `eos_token_id=None` to `model.generate` does **not** mean "no EOS" — Transformers falls back to `generation_config.eos_token_id`, i.e. exactly the mismatched value this fix exists to override. So in the one case where resolution returned empty, the code silently re-enables the defect it repairs. Two reasonable implementors will read `or None` as either "explicitly unset" or "fall back", which is build-blocking ambiguity. Fix: either (a) omit the kwarg entirely when the list is empty (`**({"eos_token_id": ids} if ids else {})`), or (b) treat an empty resolution as a loader error at `prepare_native_prompt`, since a native chat decoder with zero resolvable EOS is a load-time defect, not a generation-time one. Prefer (b) for the writer/constrained JSON routes; state one choice in the plan so all four factories match.

3. **[tests/test_writer_sampling_seed.py, new `test_both_generate_paths_are_seeded`]** The unseeded negative control asserts `draws[0] != draws[1] != draws[2]`. Chained `!=` does not assert `draws[0] != draws[2]`, and more importantly this is a probabilistic assertion on `torch.rand(4)` — correct in practice but it is the same category of brittleness as the AST line-distance test it replaced. Fix: assert `len({tuple(d) for d in draws}) == 3` and note in a comment that collision probability is negligible for 4 float32 draws; that both states the real invariant and covers the 0-vs-2 pair. Also confirm this test's third call is genuinely exercising the `_min_p_unsupported` remembered path — `min_p_values == [.05, None, None]` asserts three generate calls, but the diff shows `_min_p_unsupported[0]` is module/closure state; verify: whether `_min_p_unsupported` is reset between tests, or the *first* call of a later test in the same session already starts with min_p disabled, making `min_p_values[0] == .05` order-dependent.

# SHOULD-FIX

1. **[_native_token_ids, loader @2270]** Sorting only when the input is a `set` is a defensible determinism fix, but it means `pad_token_id` for a set-valued `tokenizer.eos_token_id` is `min(ids)` while for a list it is `ids[0]`. That is two different pad tokens for the same logical config. Since padding is only used for right-pad masking on batch-size-1 generation it is harmless today, but document it in the docstring as "pad is any valid terminator; order is incidental" so a future reader does not treat it as a contract. The new test `test_native_eos_collection_normalization_keeps_padding_scalar` currently *encodes* `pad_token_id == 19999` as a contract — weaken that assertion to `prepared["pad_token_id"] in prepared["eos_token_ids"]`.

2. **[_otr_constrained_generate @130-143]** Cache invalidation compares `cache.get("eos_token_ids") != eos_ids` where `eos_ids` is a `tuple` and the stored value is a `tuple` — correct. But the *caller-supplied* `eos_token_ids` list comes from `prepared`, resolved once per call, while the `None` default re-resolves from `cache_entry`. Two callers on the same warm entry (writer with explicit IDs, some other path with default) can therefore thrash the cache and rebuild the 256K-token scan repeatedly. Fix: have `make_constrained_generate_fn` and the writer be the only callers with explicit IDs (they already are), and note in the docstring that the `None` default exists for tests only — or drop the default entirely and require the kwarg, which removes the divergence.

3. **[Writer DECODE RETURNED log, @1116]** The log is emitted before guard classification, which is the right order, and the review text correctly states success is not inferred from `ended_with_eos` when `guard.hit` is true. Add the length to the message (`generated_tokens` is already there — sufficient). Lower priority: this is observability only.

So min_p=.05 / top_p=.92 / repetition_penalty=1.03 remain untested as the loop mechanism, and the exact hidden generated EOS sequence was not persisted, so P0's `verbatim_cycle at 672 tokens` is also unexplained by this fix. Do not let the ledger imply otherwise. Keep P1 in the denominator; keep `primary_ladder_exhausted at 400.67s` as a repetition failure, not a cancellation, exactly as written.
