## Build 1 — extract `_check_parse_ok` helper + 18-test unit test

`nodes/story_orchestrator.py` now exposes module-level compiled regexes and a
helper:

```python
import re as _re_for_parse_check

_PARSE_CHECK_SCENE_RE = _re_for_parse_check.compile(
    r'^\s*===\s*SCENE\s+\d+\s*===\s*$', _re_for_parse_check.MULTILINE
)
_PARSE_CHECK_VOICE_RE = _re_for_parse_check.compile(
    r'^\s*\[VOICE:\s*[A-Z_]+', _re_for_parse_check.MULTILINE
)
_PARSE_CHECK_BARE_RE = _re_for_parse_check.compile(
    r'^\s*(?!TITLE\b|SCENE\b|GENRE\b|ENV\b|SFX\b|MUSIC\b|VOICE\b|CAST\b|AUTHOR\b)'
    r'[A-Z][A-Z0-9_ ]{1,19}:\s*\S',
    _re_for_parse_check.MULTILINE,
)


def _check_parse_ok(text, *, is_ultra_smoke=False, is_tiny_smoke=False):
    text = text or ""
    has_scene = bool(_PARSE_CHECK_SCENE_RE.search(text))
    voice_hits = len(_PARSE_CHECK_VOICE_RE.findall(text))
    bare_hits = len(_PARSE_CHECK_BARE_RE.findall(text))
    if is_ultra_smoke:
        parse_ok = has_scene and voice_hits >= 2
    elif is_tiny_smoke:
        parse_ok = has_scene and voice_hits >= 4
    else:
        parse_ok = has_scene and (voice_hits + bare_hits) > 0
    return {
        "has_scene": has_scene, "voice_hits": voice_hits,
        "bare_hits": bare_hits, "parse_ok": parse_ok,
    }
```

The retry loop in `write_script` now calls this helper. New test
`tests/test_parse_retry.py` (18 tests) covers the three contracts (standard,
ultra-smoke, tiny-smoke) plus the loop behavior (bad-then-good succeeds on
attempt 2; both-bad exhausts retries without raising; first-good
short-circuits).

Question 1A: any concern with the secondary `import re as _re_for_parse_check`
inside the module? The module already has `import re` at the top; this second
import is a workaround to avoid touching the existing `re` symbol that other
helpers reference. Should I just use the existing `re` module-level import?

Question 1B: the ultra-smoke threshold is `voice_hits >= 2` even though the
prompt asks for 4 voice lines. Tiny-smoke is `>= 4` for ~7 lines. Are those
floors right? Too lenient (false-pass on degenerate output)? Too strict
(false-fail on a model that drops a line)?

## Build 2 — port the smoke template to `tiny (smoke, 1 act)` (100-word)

Same template shape as ultra-smoke, scaled to ~100 words across 7 dialogue
lines. The CRITICAL FORMAT RULES block is identical (bracket-form `[VOICE: ...]`
only, `=== SCENE 1 ===` once, no commentary/markdown). OpenClose was already
bypassed for `is_tiny_smoke` per round 1's must-fix, plus `max_new_tokens`
clamped to 384.

```text
TITLE: <your 3-word title>
=== SCENE 1 ===
[ENV: one-sentence setting]
[SFX: one establishing sound]
[VOICE: ANNOUNCER, female, 50s, authoritative, calm] Opening sentence. 14 words max.
[VOICE: CHARACTER_1_NAME, gender, age, tone, energy] First dramatic line. 12 words max.
[VOICE: CHARACTER_2_NAME, gender, age, tone, energy] Reaction or counter-line. 12 words max.
[SFX: action sound]
[VOICE: CHARACTER_1_NAME, gender, age, tone, energy] Second beat. 12 words max.
[VOICE: CHARACTER_2_NAME, gender, age, tone, energy] Closing exchange. 12 words max.
[VOICE: ANNOUNCER, female, 50s, authoritative, calm] Closing sentence. 14 words max.
[MUSIC: Closing theme]
```

Question 2A: the 100-word target now produces a script with 7 voice lines, ~14
words avg per line. Mistral-Nemo 12B 4-bit NF4 was the failure mode in the
original 30-word run. Will the model reliably hit "exactly 7 voice lines" or
will it drift (8 lines? 6 lines?)? The parse contract requires `>= 4`, so up to
3-line shortfall passes. Is that the right tolerance?

Question 2B: there's a second `[SFX: action sound]` cue mid-scene. Will the
model interpret that as "render an SFX cue here" or "narrate an action"? The
ultra-smoke template has only one `[SFX:]` cue, and it works. Adding a second
mid-scene cue is the only structural difference between the two templates
besides line count.

## Build 3 — light type validation in `scripts/otr_api.py::patch_widget_by_name`

New helpers `_spec_for` and `_validate_widget_value`. `patch_widget_by_name`
now validates the value's TYPE/CHOICES against the declared widget spec
before writing:

* COMBO values must be in the declared choice list (case-sensitive,
  no fuzzy matching).
* INT enforces Python `int`; bool is REJECTED even though `bool` is a subclass
  of `int` (mistaken True/False routed to a numeric widget is a real bug class).
* FLOAT accepts int OR float; bool rejected.
* BOOLEAN/BOOL enforces `bool` (rejects 1/0 int).
* STRING enforces `str`.
* `None` is permissive (treated as "use default").
* Unknown spec types are skipped (best-effort, never block).

Test coverage in `tests/test_otr_api_type_validation.py` (28 tests):
TestSpecFor (4), TestValidationHappyPaths (6), TestValidationRejections (12),
TestPatchWidgetByName (6).

Question 3A: the `bool` rejection on INT widgets is intentional — caller passes
`True` thinking they're enabling a feature, and it lands in a numeric field
silently. But `bool` IS an int in Python. Some ComfyUI workflows use 1/0 for
boolean toggles. Will this rejection break any legitimate caller? Should I add
an opt-out flag or a coerce-bool-to-int mode?

Question 3B: COMBO validation is case-sensitive: `"Balanced"` is rejected when
the choice list has `"balanced"`. This catches typos but might be too strict
when a workflow JSON ships with a slightly-different capitalization than the
node's current declared list (e.g. node was renamed "Balanced" -> "balanced"
between versions). Should the validation be case-insensitive with a warning,
or stay strict?

Question 3C: `_spec_for` raises KeyError when the widget is not declared.
Combined with the existing `widget_name not in widget_names` check in
`patch_widget_by_name`, this is now a redundant lookup. Should I cache the
spec in `patch_widget_by_name` and pass it to `_validate_widget_value`?
