## Build 1 — extract `_check_parse_ok` helper + 18-test unit test

`nodes/story_orchestrator.py` now exposes module-level compiled regexes and a
helper:

```python
import re as _re_for_parse_check

_PARSE_CHECK_SCENE_RE = _re_for_parse_check.compile(
    r'^\s*===\s*SCENE\s+\d+\s*===\s*$', _re_for_parse_check.MULTILINE
)
_PARSE_CHECK_VOICE_RE = _re_for_parse_check.compile(
    r'^\s*\[VOICE:\s*[A-Z_]+', _re_for_parse_check.MULTILINE
)
_PARSE_CHECK_BARE_RE = _re_for_parse_check.compile(
    r'^\s*(?!TITLE\b|SCENE\b|GENRE\b|ENV\b|SFX\b|MUSIC\b|VOICE\b|CAST\b|AUTHOR\b)'
    r'[A-Z][A-Z0-9_ ]{1,19}:\s*\S',
    _re_for_parse_check.MULTILINE,
)


def _check_parse_ok(text, *, is_ultra_smoke=False, is_tiny_smoke=False):
    text = text or ""
    has_scene = bool(_PARSE_CHECK_SCENE_RE.search(text))
    voice_hits = len(_PARSE_CHECK_VOICE_RE.findall(text))
    bare_hits = len(_PARSE_CHECK_BARE_RE.findall(text))
    if is_ultra_smoke:
        parse_ok = has_scene and voice_hits >= 2
    elif is_tiny_smoke:
        parse_ok = has_scene and voice_hits >= 4
    else:
        parse_ok = has_scene and (voice_hits + bare_hits) > 0
    return {
        "has_scene": has_scene, "voice_hits": voice_hits,
        "bare_hits": bare_hits, "parse_ok": parse_ok,
    }
```

## Q1A — secondary `import re as _re_for_parse_check`

I would remove the secondary import and use the existing module-level `re`.

The current alias is technically harmless:

```python
import re as _re_for_parse_check
```

Python will reuse the already-loaded module from `sys.modules`; this is not a runtime/performance issue.

But architecturally it is noise. It makes the module look like there is a special parse-check regex dependency when there is not. If the file already has:

```python
import re
```

then this is clearer:

```python
_PARSE_CHECK_SCENE_RE = re.compile(...)
```

I would only keep the alias if the existing `re` name is genuinely unstable, e.g. overwritten later at module scope, which would itself be a bigger smell. Based on your description, this does not sound necessary.

**Recommendation:** change to the existing `re` import.  
**Blocking?** No.

## Q1B — ultra-smoke `voice_hits >= 2`, tiny-smoke `voice_hits >= 4`

I think these floors are acceptable for smoke mode.

Important distinction:

- The prompt asks for a target shape.
- The parse gate should answer: “Is this minimally renderable?”
- It should not become a quality evaluator, especially after Round 1’s requirement to bypass OpenClose before the 3-outline evaluator.

For ultra-smoke, `voice_hits >= 2` is lenient, but defensible. Ultra-smoke is the fastest possible pipeline sentinel. If it has:

```text
=== SCENE 1 ===
[VOICE: ...]
[VOICE: ...]
```

then it is probably enough to prove that the script path, voice parsing path, audio synthesis path, muxing path, and output path are alive.

If you made ultra-smoke require `>= 4`, you would reduce degenerate passes, but you would also reintroduce the old failure mode where the smoke test fails because the LLM missed one tiny formatting requirement.

For tiny-smoke, `voice_hits >= 4` against a 7-line target is also reasonable. It tolerates:

- one or two dropped lines,
- one malformed voice tag,
- minor LLM drift,

while still rejecting truly unusable output.

I would not tighten these right now.

**Recommendation:** keep:

```python
ultra-smoke: voice_hits >= 2
tiny-smoke:  voice_hits >= 4
```

But I would make sure the test names/comments explicitly describe these as **minimum renderability floors**, not exact prompt compliance.

**Blocking?** No.

## Q3A — rejecting `bool` for INT widgets

I agree with the rejection.

In Python:

```python
isinstance(True, int) == True
```

but accepting `True` for an INT widget is a classic silent configuration bug. For this project, fail-fast behavior is better than permissive coercion.

Example bad case you are explicitly preventing:

```python
patch_widget_by_name(workflow, "seed", True)
```

becoming:

```python
seed = 1
```

That is exactly the kind of silent mutation that undermines reproducibility and makes C7 debugging miserable.

Some ComfyUI workflows do use `1`/`0` for boolean-ish toggles, but that is different from allowing `True`/`False` into declared INT widgets. If a widget is declared INT, callers should pass `1` or `0`, not `True` or `False`.

I would not add an opt-out flag yet. It increases API surface area before there is a proven need.

**Recommendation:** keep strict bool rejection for INT and FLOAT.  
**Blocking?** No.

---

## Q3B — case-sensitive COMBO validation

I would keep COMBO validation case-sensitive.

For a local deterministic pipeline, this is the safer behavior:

```python
"balanced" != "Balanced"
```

If the declared choice list says:

```python
["fast", "balanced", "quality"]
```

then passing:

```python
"Balanced"
```

should fail loudly.

Case-insensitive repair sounds convenient, but it introduces silent migration behavior in a generic patching function. That can become dangerous if choices differ only by capitalization or if a future node uses case intentionally.

If a node changes from `"Balanced"` to `"balanced"` between versions, I would handle that with an explicit migration layer or workflow-version adapter, not inside the generic widget patcher.

**Recommendation:** stay strict. Add migrations only for known version transitions.  
**Blocking?** No.

# One thing to double-check: `None` behavior

You wrote:

> `None` is permissive — treated as “use default”.

That is fine **only if `patch_widget_by_name` skips writing the value** when `value is None`.

This is good:

```python
if value is None:
    return  # leave existing/default workflow value untouched
```

This is risky:

```python
widgets[index] = None
```

because most ComfyUI widgets will not interpret JSON `null` as “use default.” They will usually receive `None`, which may crash later or change behavior.

I am not blocking because I have not seen the actual implementation, and your tests may already cover this. But I would explicitly verify that “None means default” does not accidentally mean “write null into the workflow.”

Suggested test if not already present:

```python
def test_patch_widget_none_leaves_existing_value_unchanged():
    ...
```

If the current code writes `None` into the widget array, I would fix that before the mega-commit.
