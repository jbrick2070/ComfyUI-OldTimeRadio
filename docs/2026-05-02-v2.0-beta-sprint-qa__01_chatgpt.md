# Change 1 — BUG-LOCAL-005: 30-word ultra-smoke prompt branch

## 1A. Is the prompt likely to produce parseable output?

**Mostly yes, but not reliably enough by itself.**

For Mistral-Nemo 12B 4-bit NF4, the prompt is much better than the standard story prompt for a 30-word pipeline ping. It gives:

- explicit `TITLE:`
- explicit `=== SCENE 1 ===`
- bracketed `[VOICE: ...]` lines
- no prose / no markdown instruction
- small line count
- clear parser-dependent formatting

That is the right shape.

However, likely failure modes remain:

1. **Model outputs markdown fences or commentary anyway**

   ```text
   Here is the script:
   TITLE: Signal Test
   ...
   ```

   If the parser requires `TITLE:` as first line, this can still fail unless there is cleanup.

2. **Model leaves placeholders**

   ```text
   [VOICE: CHARACTER_1_NAME, male, 30s, tense, low] Hello.
   ```

   Parseable structurally, but bad downstream if voice assignment expects real roster names.

3. **Model uses bare speaker labels despite prohibition**

   ```text
   ANNOUNCER: Signal lost.
   ```

   The smoke prompt forbids this, but Nemo may still do it.

4. **Model generates the requested structure but too many words**

   Not fatal for parser/audio, but defeats the “smallest possible script” goal and can inflate later work.

5. **Model omits the scene marker**

   This is the big one. You can get `[VOICE: ...]` lines but no `=== SCENE 1 ===`, leading to zero parsed scenes depending on parser strictness.

6. **Model generates only title / metadata / outline**

   With the current Change 2 regex, this can falsely pass because `TITLE:` is counted as a bare dialogue hit.

### Must-fix recommendation

For ultra-smoke, do not rely on a generic “one marker exists” check. Require at least:

```python
has_scene = bool(re.search(r'^\s*===\s*SCENE\s+1\s*===\s*$', script_text, re.MULTILINE))
voice_hits = len(re.findall(r'^\s*\[VOICE:\s*[^\]\n]+?\]\s*\S', script_text or "", re.MULTILINE))
```

Then for 30-word ultra-smoke:

```python
if has_scene and voice_hits >= 3:
    PARSE_OK
else:
    retry
```

The prompt asks for 4 voice lines, but requiring 3 gives a little model tolerance while still avoiding degenerate passes.

Also clamp `max_new_tokens` for this branch. The failed run produced 571 tokens for a 30-word smoke test. That is already too much.

Suggested ultra-smoke cap:

```python
if is_ultra_smoke:
    max_new_tokens = min(max_new_tokens, 256)
```

Maybe 320 if your tags/roster names are verbose, but not 1000+.

## 1B. Should this branch also apply to “tiny (smoke, 1 act)” / 100 words?

**Yes, probably.**

If “tiny” is intended as a pipeline ping, not a narrative quality test, it should not use the full standard script prompt and should not depend on OpenClose. The 100-word path should get a separate smoke prompt, not necessarily the exact 30-word template.

Recommended split:

- `30 words` → ultra-smoke, 1 scene, 4 voice lines, `max_new_tokens <= 256`
- `tiny`, `smoke`, `100 words`, `1 act` → tiny-smoke, 1 scene, maybe 6–8 voice lines, `max_new_tokens <= 384` or `512`

The important part is not word count. The important part is: **skip outline/evaluator complexity and require parser-native structure.**

# Change 2 — BUG-LOCAL-004: KV-cache flush + parse-retry cap

## 2A. Is `empty_cache()` enough? Should you delete `past_key_values` / `DynamicCache`?

Short answer: **`empty_cache()` alone is not a full fix, but explicitly deleting `model.past_key_values` is probably not the right primary fix either.**

In normal Hugging Face `generate(...)` usage, the KV cache is local to the generation call. It is not usually stored permanently on the model object after generation unless your wrapper stores returned generation outputs, returns `past_key_values`, uses a persistent static cache, or keeps references alive through logging/ledger/callback closures.

Because `_LLM_CACHE` holds the model weights, not normally the per-call KV cache, this:

```python
torch.cuda.empty_cache()
```

only releases unreferenced cached allocator blocks. It does **not** free tensors that still have live Python references.

So the real question is: inside `_generate_with_llm(...)`, are any of these retained after return?

- tokenized `inputs`
- `input_ids`
- `attention_mask`
- generated tensor
- returned `GenerateOutput`
- `past_key_values`
- logits / scores / attentions
- live ledger closures capturing tensors
- exception objects holding traceback frames with tensors

### Recommended fix location

Look in the implementation of:

- `nodes/story_orchestrator.py` or wherever `_generate_with_llm(...)` is defined/imported from

At the end of `_generate_with_llm(...)`, make sure it does something like:

```python
try:
    # decode to plain Python str first
    text = tokenizer.decode(...)

    return text
finally:
    for _name in (
        "inputs",
        "input_ids",
        "attention_mask",
        "outputs",
        "generated_ids",
        "generation_output",
    ):
        if _name in locals():
            try:
                del locals()[_name]
            except Exception:
                pass

    gc.collect()
    if torch.cuda.is_available():
        torch.cuda.empty_cache()
```

You cannot literally rely on `del locals()[name]` in all cases because modifying `locals()` is not guaranteed to clear fast locals. Better is explicit `del inputs, outputs, ...` where available.

I would **not** add random mutation like:

```python
model.past_key_values = None
```

unless you have verified that your model/wrapper actually sets it. Most `transformers` causal LM models do not retain it there after `generate()`.

### Bigger issue

The reported 29.5 GB peak on a 16 GB device suggests one or more of:

- OpenClose generated multiple long-ish prompts before the final script generation.
- KV/cache tensors were still referenced after previous calls.
- `max_new_tokens` was far too high for smoke.
- context length remained near 16k for a tiny prompt.
- generation returned scores/logits/attentions.
- live ledger retained GPU tensors.
- exception tracebacks kept tensors alive.
- the model used an unexpectedly memory-heavy cache implementation.

Given the owner’s constraint — no low-level VRAM optimization chase — the highest-payoff fixes are:

1. **Bypass OpenClose entirely for smoke/tiny.**
2. **Clamp `max_new_tokens` for smoke/tiny.**
3. **Fix `_generate_with_llm(...)` to not retain outputs/caches.**
4. **Flush after each LLM call, not only before the main call.**

## 2B. Should ultra-smoke use strict `[VOICE:]` only?

**Yes. For ultra-smoke, strict `[VOICE:]` only.**

The generic permissive check is reasonable for legacy/standard paths if the parser supports bare labels. But the ultra-smoke prompt explicitly says:

> The bracket-form `[VOICE: ...]` is the ONLY accepted dialogue tag here.

So the validation should match that contract.

Also, again, the current bare regex is dangerous because it accepts non-dialogue labels like:

```text
TITLE:
GENRE:
AUTHOR:
CAST:
```

For ultra-smoke, I would use:

```python
has_title = bool(re.search(r'^\s*TITLE:\s*\S+', script_text or "", re.MULTILINE))
has_scene = bool(re.search(r'^\s*===\s*SCENE\s+1\s*===\s*$', script_text or "", re.MULTILINE))
voice_hits = len(re.findall(
    r'^\s*\[VOICE:\s*[^\]\n]+?\]\s*\S',
    script_text or "",
    re.MULTILINE,
))
bare_hits = len(re.findall(
    r'^\s*(?!TITLE\b|GENRE\b|ENV\b|SFX\b|MUSIC\b|SCENE\b)[A-Z][A-Z0-9_ .\'-]{1,30}:\s*\S',
    script_text or "",
    re.MULTILINE,
))

if is_ultra_smoke:
    ok = has_title and has_scene and voice_hits >= 3 and bare_hits == 0
else:
    ok = has_scene and (voice_hits + bare_hits) >= 1
```

I would also change the `[VOICE:]` detector from:

```python
r'^\s*\[VOICE:\s*[A-Z_]+'
```

to something less brittle:

```python
r'^\s*\[VOICE:\s*[^\]\n]+?\]\s*\S'
```

The current pattern only counts names made of uppercase letters and underscores. It may miss valid names like:

```text
[VOICE: ANNOUNCER, female, 50s, authoritative, calm] ...
[VOICE: DR. VALE, female, 40s, tense, low] ...
[VOICE: CAPTAIN ROURKE, male, 50s, clipped, hard] ...
```

Because the regex stops at punctuation/spaces/commas, it can undercount valid output.

## 2C. Is `MAX_PARSE_RETRIES = 2` right?

**Yes, with conditions.**

Two forward passes is a reasonable hard cap for a local 16 GB machine. More retries are likely to worsen the OOM story and waste time.

But I would make the retry behavior branch-aware:

- 30-word ultra-smoke: `MAX_PARSE_RETRIES = 2`, `max_new_tokens <= 256`
- 100-word tiny-smoke: `MAX_PARSE_RETRIES = 2`, `max_new_tokens <= 384/512`
- regular short episode: `MAX_PARSE_RETRIES = 1 or 2`, but only if generation memory is proven stable
- long episodes: avoid automatic retries unless the model is unloaded/reloaded or context is segmented

Parametric by `target_words` is useful, but the more important variable is **smoke vs narrative path**.

For this commit, a simple version is enough:

```python
if is_ultra_smoke:
    max_parse_retries = 2
else:
    max_parse_retries = 2 if target_words <= 700 else 1
```

But since your changed code is already only in the short-episode branch, `2` is acceptable once the structural check is fixed.

# Change 3 — BUG-LOCAL-006: `tests/conftest.py` CUDA masking

## Anything wrong with masking CUDA via env var at conftest import?

Mostly fine, with one caveat.

Setting this at top-level in `tests/conftest.py`:

```python

os.environ["OTR_TEST_MODE"] = "1"
```

is earlier than `pytest_sessionstart`, so doing it in a session hook would generally be **worse**, not better.

However, `conftest.py` is still not the absolute earliest possible moment. Pytest plugins may already be loaded before root `conftest.py` is imported. If a plugin or site customization imports `torch` before your conftest runs, CUDA visibility may already be cached.

Your added fix in `tests/vram_profile_test.py`:

```python
torch.cuda.device_count() > 0
```

is therefore good and necessary.

### Potential gotchas

1. **Plugins importing torch before conftest**
   - Rare, but possible.
   - If this happens, `torch.cuda.is_available()` can lie based on earlier initialization.

2. **Test modules importing torch at collection time**
   - Root `conftest.py` should normally run before test module collection, so this is okay.

3. **Subprocess tests**
   - The env var will propagate to subprocesses unless overwritten. That is usually what you want.

4. **Windows behavior**
   - Empty `CUDA_VISIBLE_DEVICES` generally masks devices for PyTorch, but if you see inconsistent behavior, use:

     ```python
     os.environ.setdefault("CUDA_VISIBLE_DEVICES", "-1")
     ```

     I would not change this unless tests show the empty string fails on your pinned stack.

### Should this move to session start?

No. If anything, move earlier, not later.

The more robust options are:

- launch pytest through a wrapper script that sets the env before Python starts
- use `sitecustomize.py`
- use `pytest-env`
- create a tiny plugin using `pytest_load_initial_conftests`

But for now, root `tests/conftest.py` top-level assignment is acceptable.

# Change 4 — BUG-LOCAL-002: `scripts/otr_api.py`

## Is the stripped/preserved widget inference safe?

Yes. The “raise rather than patch the wrong slot” behavior is the right choice.

Given ComfyUI workflow JSON instability, this is exactly the right risk posture. Wrong-slot patching is dangerous because it can silently alter:

- prompt
- seed
- duration
- voice model
- sampler
- filename
- audio parameters

For this project, silent wrong-slot mutation is worse than a hard failure because of rule C7: audio output must remain byte-identical at gates.

## Are there third widget shapes?

Possibly. I would not claim your two-shape model covers every ComfyUI version/custom-node workflow forever.

Common shapes you are handling:

1. **Preserved**
   - `widgets_values` includes entries for all declared widgets.

2. **Stripped**
   - widgets converted to input sockets are omitted from `widgets_values`.

Possible awkward cases:

1. **Trailing default omission**
   - Some serializers/tools may omit trailing defaults.

2. **`None` placeholders**
   - Converted widgets may remain as `None` instead of being stripped.

3. **Custom node schema drift**
   - Node declares widgets differently between saved workflow and runtime `/object_info`.

4. **Dictionary-like widget storage**
   - Less common for standard UI workflow JSON, but third-party editors may produce non-list structures.

5. **Extra hidden widgets**
   - Some nodes have internal/control widgets like seed behavior, control-after-generate, etc.

Your current “if neither length matches, raise” is still the safe choice.

## Should you assert expected widget type?

**Yes, lightly.**

Do not over-engineer it, but basic validation is valuable.

Recommended:

- For `COMBO`, assert the patched value is one of the declared choices unless the schema has dynamic choices.
- For `INT`, accept `int` and reject non-integral strings unless explicitly coercing.
- For `FLOAT`, accept `int`/`float`.
- For `STRING`, accept `str`.
- For `BOOLEAN`, accept `bool`.

But avoid being too strict with ComfyUI’s inconsistent metadata. If type info is missing or ambiguous, warn or skip type validation rather than breaking valid workflows.

I would add this as a follow-up unless `patch_widget_by_name` is touching C7-critical audio settings. For audio settings, type validation should be a must.
