2. [v0 step 2 / OTR_LedgerScriptWriter F2 / _otr_story_quality_l12.build_sq_data] Defect: scoring with `build_sq_data` mutates `beat.intent` in place. The plan then says “everything downstream ... F2 build_sq_data ... runs on the winner unchanged,” which means the winning outline can be shaped once during scoring and shaped again in F2. This is not idempotent: `_enrich_intent()` can append another personal-stake / irreversible-choice tail when `has_obj` is false, especially for `personal_stake`, because the first appended tail does not include the conflict object. Concrete fix: ensure `build_sq_data` is called exactly once on the winner. Options: score on a deep copy and discard the mutation, then let F2 run once; or have the selector return `(winner_outline, winner_sq_by_beat)` and skip/reuse F2 for the winner. Also add a regression test for no duplicate appended clauses.

Concrete fix: either update the invariant to allow the existing L1/L2 intent-only mutation, or add a pure scoring mode to `_otr_story_quality_l12` that computes SQ metrics without mutating the candidate outline.
