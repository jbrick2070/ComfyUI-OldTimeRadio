## What the bug is, in one paragraph

We assumed `WanHuMoImageToVideo`'s `ref_image` parameter would do generic I2V (use the input image as the first frame / strict visual condition). It does not. Reading the upstream stock node body in `comfy_extras/nodes_wan.py:1070-1108`, `ref_image` is VAE-encoded into a soft `reference_latents` field appended to the positive conditioning, and the actual generation latent starts from zeros. HuMo is a face-locked audio-to-talking-head model: the reference is intended as a face-identity hint so the rendered character stays consistent across the clip. When the reference is a non-face image (we passed a 1940s broadcast-radio still rendered by FLUX), the identity attention has nothing to lock to, and HuMo defaults to text-prompt-driven face generation. With per-line seeds `(seed + idx*1009)`, two ANNOUNCER lines (l001 idx=0, l021 idx=20) rendered as two different generic blonde women, while the radio still that the ledger claims was used was completely ignored.

This breaks the architectural premise in `nodes/_otr_speaker_role.py:12-22` which declares "announcer → radio still, music_* → radio still, sfx → radio still — the radio is the visual performer for everything that isn't dialogue." HuMo physically cannot animate the radio. Wall-to-wall HuMo coverage is incompatible with the radio being the non-dialogue visual.

### Where Gemini and NVIDIA corrected ChatGPT (and my framing in the question)

The question and ChatGPT's answer both implied that `WanHuMoImageToVideo`'s `reference_latents` mechanism is *itself* what makes the model face-only. **Gemini and NVIDIA both flagged this as imprecise, and they're right.** The `reference_latents` injection via `node_helpers.conditioning_set_values(positive, {"reference_latents": [ref_latent]}, append=True)` at `comfy_extras/nodes_wan.py:1077` is the **standard generic Wan2.1 I2V conditioning path** — it is not specific to HuMo. What restricts the rendered output to face animation is the **HuMo finetuned weights**, not the conditioning code. A different Wan2.1 checkpoint loaded against the same node could in principle animate non-human references; HuMo specifically cannot because that's how it was trained.

This matters for BUG-LOCAL-129 documentation accuracy: the architectural premise in `_otr_speaker_role.py` is incompatible with HuMo's *weights*, not with the I2V node's *code*. Same conclusion (radio still cannot be the per-line visual performer when HuMo is the renderer), but the framing should not paint the stock node's conditioning mechanism as broken.

ChatGPT also asserted that "ffmpeg concat introduces a resample" as a C7 risk — both Gemini and NVIDIA pushed back: `-c:a copy` is bit-exact and physically cannot resample. If you're using `-c:a copy` you're safe; if you aren't, you're already violating C7. This is a clean correction.

### What Gemini added that the others missed

**C7 muxing architecture (most important).** When mixing HuMo clips with static radio clips, you cannot concatenate mixed audio+video chunks because container repacketization will alter audio bytes even with stream-copy. The pattern that actually preserves byte-identity is: assemble a **video-only** stream (all clips concatenated with `-an`), then do a **single final mux** of the pristine master audio over the concatenated video using `-c:v copy -c:a copy`. Gemini specifically called out that `_render_master_mix_per_clip_mux_mode` should be reviewed against this pattern. (Possibly relevant to BUG-LOCAL-128 audio-truncation as well.)

**Frame math for static clips.** Audio durations rarely land on perfect frame boundaries (e.g., 1.05 s = 26.25 frames at 25fps). A strict frame-rounding policy (e.g., `round(audio_duration * HUMO_FPS)`) is needed for static `music_*`/`sfx` clip generation to prevent cumulative A/V desync across a long episode. Without this, drift accumulates per-clip.

### What NVIDIA added that the others missed

**Frame-rate consistency.** OTR's HuMo runs at `HUMO_FPS = 25` (per `nodes/batch_humo_render.py:200`); ffprobe of today's final mp4 confirmed `r_frame_rate=25/1`. Static `music_*`/`sfx` clips must therefore also be 25fps, NOT 24fps. The question's draft proposed 24fps for static fills — that would create frame-rate mismatches at concat time. **Lock everything to 25fps.**

**Aspect ratio / resolution.** ANNOUNCER portraits rendered by FLUX must match HuMo's expected resolution (the workflow currently runs FLUX at 1024x1024 and HuMo internally at 832x480 default per `comfy_extras/nodes_wan.py:1054-1055`, but our workflow may override). Mismatch produces distortion. Verify the FLUX width/height widget for the ANNOUNCER portrait matches HuMo width/height in the OTR workflow before relying on it.

**SFX overlap handling.** SFX playing UNDER dialogue (door slam during a line, ambient texture during speech) should NOT cut to a separate visual. SFX in that case is part of the dialogue line's audio; the visual stays on the speaking character. Only standalone SFX (no concurrent dialogue) gets a static-video treatment. Gemini also flagged this as an unknown.
