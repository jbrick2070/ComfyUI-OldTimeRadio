## THE LIVE BUG

`config/profiles/otr_8gb_wan.json` pinned `video.max_render_frames: 17` (and
its env twin `OTR_WAN_TI2V_MAX_FRAMES: "17"`). That was a real low-VRAM launch
contract when it was written. It became a bug **without anyone touching it**:
on 2026-08-02 `wan_ti2v` was added to `frame_contract.PLANNING_CAP_ENGINES` and
the adapter-side ping-pong that made a render cap harmless was ripped the same
day. From that moment the pin narrowed the PLANNER, so every beat on that
profile became a chain of 0.68-second segments -- the exact "pile of 17-frame
renders" the adapter's own comment warned against, while that same comment
claimed WAN was "deliberately excluded from PLANNING_CAP_ENGINES".

The comment described protection that had been deleted. Both are fixed: the pin
is 81 (= 4*20+1, on the shared ladder, the value its sibling WAN and FastWan
profiles already carry), and the comment now says what is true.

**AND THREE TESTS WERE DEFENDING THE BUG.**
`test_otr_8gb_wan_profile_pins_low_vram_contract`,
`test_applied_8gb_variant_pins_17_and_other_tiers_stay_unpinned` and
`test_the_wan_8gb_variant_still_carries_its_real_17_frame_ceiling` all asserted
17 as correct. They were right when written and went stale silently, which is
the most expensive kind of test: it makes the fix look like the regression. Two
now assert against the PROFILE rather than a literal, so the number can move
again without the tests lying either way.

**NOT RE-MEASURED ON 8 GB HARDWARE.** This profile exists to serve an 8 GB
card, and 81 frames at 832x480 has not been proved to fit there. If it does not,
the answer is a MEASURED ceiling, not a return to a number that breaks the
planner. Queued rather than assumed.

## The first naming MOVE

`wan_8gb` did not stay a second public row -- it MOVED into
`_LEGACY_ENGINE_ALIASES`. Two public ids on one internal id collapses
`_INTERNAL_TO_PUBLIC` and trips the module-scope bijection assert at IMPORT
time, and because the director imports that module unguarded, the blast radius
is most of OTR vanishing from the ComfyUI node menu rather than one lane failing
cleanly. Verified live: `wan_8gb`, `wan_8gb (16:9)`, `wan22_high_video` and
`wan_ti2v` all resolve; `wan_8gb` appears in NO menu option; the menu is still
27 rows.

## A second drift class, found by the fix

`workflows/variants/*.env.json` is **not** generated by
`scripts/build_variants.py` -- only four exist and they are kept by hand. So
regenerating the variant rewrote the graph and the launch recipe and left the
env recipe behind, still saying 17, and still carrying a stale `master_hash`
for a graph that no longer existed. Both are corrected, and both now have
standing guards (`test_the_hand_kept_env_recipe_cannot_drift_from_its_profile`,
`test_the_hand_kept_env_recipe_carries_the_LIVE_master_hash`) so the next mover
is told rather than finding out in a leg.
