# Video evidence manifest (spec S9)

`video_evidence_manifest.json` is GENERATED by
`scripts/build_video_evidence_manifest.py`. Edit the script's `ROWS` table and
regenerate; never hand-edit the JSON.

## What it is for

Lesson L7 in `docs/LANE_BUILD_LESSONS.md`: a number without its evidence key is
not evidence. Every numeric claim the video build makes must carry engine,
recipe and quant, canvas, measured model-frame rung, delivered frame count,
boot lane, cache state, measurement surface, wall-time boundary, receipt path,
receipt SHA-256, and a Git commit that CONTAINS the receipt.

The last item is the one that bites. A SHA-256 of a file that is not shipped
proves nothing to a reader without it, so every row records
`contained_in_evidence_commit` -- the result of
`git cat-file -e <lab_evidence_commit>:<path>` -- separately from
`present_on_disk`.

in the lab working tree but were never committed:

- `docs/ENVELOPE_LADDERS.md`, `docs/WAN_RETENTION_FINDINGS.md`,
  `docs/H3_MUSIC_FOLLOWUP.md`
- both HuMo 14B diet landscape receipts and both portrait receipts
- `h3_i2v_canonical_832x480_f107_run1.json`
- `h3_music_followup_score_seed42_f192_run1.json`
- all three `otr_side/wan_retention/` phase receipts

So those rows are numerically supported by files on this box and are NOT
reproducible from the stated baseline. The manifest says so per row instead of
printing the numbers as if the baseline held. Fixing it means committing those
receipts to a new lab evidence commit and bumping `lab_evidence_commit` here --
that is lab-side work, not an OTR code change, and it does not block a lane.

## What a `qa_verdict` means

Carried forward verbatim from the independent QA pass
(`docs/2026-08-10-FINAL-QA-video-build-corpus.md`), because a verdict that
contradicts the corpus's own wording is the most valuable thing in the row:

| Verdict | Meaning |
|---|---|
| `SUPPORTED` | the receipt says what the corpus says |
| `SUPPORTED_COLD` | supported, but the receipt is a COLD gate; no warm pass exists |
| `SUPPORTED_WITH_QUALIFIER` | supported only on a stated surface (e.g. OTR-side, one orientation, one rung) |
| `PARTIAL` | part of the stated range has a receipt and part does not |
| `NUMERICALLY_SUPPORTED` | the numbers are right; the stated baseline commit does not contain them |
| `UNSUPPORTED_AS_WRITTEN` | the receipt exists and disagrees with the corpus wording |
| `DIAGNOSTIC_ONLY` | a whole-child / chained measurement, never a single-render envelope |
| `FAILED_DIAGNOSTIC` | a failed run, at a different canvas; decides nothing |
| `MEASURED_BELOW_RANGE_FAILURE` | a failure below the model's trained range: evidence against, never evidence for a floor |
| `PARTIAL_WRONG_SURFACE` | real receipt, wrong question -- it cannot classify the lane it was being quoted for |

## `admission_unenforced`

Preflight gate G4.1 says a lane either has a QUALIFIED cost row / envelope key,
or its receipts say "admission NOT enforced" IN WORDS, on disk, reachable in
the manifest. That table is where those words live, and
`tests/test_lane_preflight_matrix.py` reads it.

`QUALIFIED_COST_ROWS` is empty today (`motion_common.py:386`), so NO local lane
is guarded -- and since 2026-08-13 that is true on BOTH refusal paths. The
STATIC path (`compute_real_frame_budget`, reached from
`eng_wan_ti2v._floor_length`) used to refuse anyway, because it never asked
`cost_row_may_refuse`; it took two live 45-word render-gate legs before anyone
noticed the authority was wired to only one of its two call sites. A silently unguarded lane that looks guarded is the failure this
mechanism exists to prevent; a lane leaves the table in the same commit that
qualifies its cost row through OTR's real `prepare()` + `render_clip()`
lifecycle -- never from lab numbers alone.
