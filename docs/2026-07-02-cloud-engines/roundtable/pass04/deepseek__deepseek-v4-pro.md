VERDICT: yes-with-fixes. The plan is nearly converged but contains two build-blocking ambiguities in the invocation contract and one residual defect in the reactivity gate that could cause silent wrong-behavior in production.

MUST-FIX BEFORE BUILD:
1. [Sec 3] `invoke_partner_node` signature lists `session` as a parameter, but Sec 2 states adapters FETCH the session from the backend table and "No AudioEngine signature change." These are contradictory. If `invoke_partner_node` takes `session`, then every adapter call site must pass it, which IS a signature change to the frozen AudioEngine protocol. Concrete fix: remove `session` from the invoke signature and state that `invoke_partner_node` internally resolves the session from the backend table keyed by the current prompt_id (obtained from hidden inputs). The adapter never receives or passes a session object.
2. [Sec 3] `invoke_partner_node` returns `PartnerResult` but the plan never defines this type. A reasonable implementor would invent two different shapes (one with raw bytes, one with a file path). Concrete fix: define `PartnerResult` as a TypedDict with at minimum `{"data": bytes, "content_type": str, "duration_s": float | None}`. State that the canonicalizer consumes this shape.
3. [Sec 5] The reactivity gate says "talking/announcer beats reject engines whose reactivity is not required_audio_ref or lipsync_overlay." But `required_audio_ref` and `lipsync_overlay` are values of the `reactivity` descriptor field. The plan does not specify WHERE this check lives (ShotLock? VideoDirector? adapter assert_usable?) or what error it raises. If it lives in ShotLock, it must happen BEFORE the cloud dispatch (Sec 2 says "named queue-time error BEFORE money is spent"). If it lives in adapter assert_usable, it must be called before invoke. Concrete fix: state that `OTR_ShotLock.validate()` performs this check immediately after resolving the engine pick, raises `EngineUnusable(…, reason=INCOMPATIBLE_PROFILE)` with a message naming the required reactivity, and that this runs before any cloud reservation.

SHOULD-FIX:
4. [Sec 2] The budget state machine defines states RESERVED -> SUBMITTED -> BILLED_ESTIMATE | BILLED_ACTUAL, with RELEASED and ABORTED. But the plan never specifies WHO drives these transitions — the adapter, the session, or the broker. A reasonable implementor could put the state machine in the adapter (tight coupling) or in the session (clean but requires adapter cooperation). Concrete fix: state that the session object owns the state machine and exposes `reserve(estimate_usd) -> reservation_id`, `submit(reservation_id, job_id)`, `bill(reservation_id, actual_usd)`, `release(reservation_id)`, `abort(reservation_id)`. Adapters call these methods.
5. [Sec 4] CloudAssetKey includes sha256 computed AFTER canonicalization mutations. The plan says "a stripped video hashes as its delivered bytes." But the canonicalizer runs AFTER the cloud provider returns bytes — does the cache lookup happen on the pre-canonicalization bytes (provider raw) or post-canonicalization bytes? If the cache key uses post-canonicalization hash, you must canonicalize before you can check the cache, which defeats the purpose. Concrete fix: state that the cache key uses the hash of the PROVIDER-RAW bytes (pre-canonicalization), and the cache manifest records the canonicalizer version. On cache hit, re-canonicalize if the manifest version is stale. The sha256 in the key is of the raw download.
6. [Sec 7] The rows table lists `cloud$ nano_banana_2` under STILLS but this name does not appear in any grounding excerpt. It may be a real partner node or a placeholder. If it ships, the yaml must pin it. If it's speculative, cut it. Concrete fix: either confirm the class exists in the partner nodes or replace with a known candidate from the checked-in yaml.
