# BUG-LOCAL-129 architectural fix — HuMo cannot animate the radio still

## Project context (constraints, no negotiation)

- **Hardware:** RTX 5080 Laptop, 16 GB VRAM, Blackwell sm_120, single GPU, Windows, Python 3.12, torch 2.10.0, CUDA 13.0. SDPA + SageAttention only. No FA2/3, no cloud, no API keys, 100% local, offline-first.
- **VRAM ceiling:** 14.5 GB peak, no exceptions. `force_vram_offload()` is forbidden between LLM phases (use `_flush_vram_keep_llm()`).
- **Audio rule (C7):** final episode audio must be byte-identical to v1.5 baseline at every gate. If video work breaks audio, revert immediately.
- **Audio is king.** Full narrative output never breaks, shortens, or degrades to satisfy a video constraint.
- **Project:** ComfyUI-OldTimeRadio, branch v2.0-alpha, commit 620013e. v2.0 architecture is "wall-to-wall HuMo coverage" — every audio second is a HuMo lip-sync clip.

## What the bug is, in one paragraph

We assumed `WanHuMoImageToVideo`'s `ref_image` parameter would do generic I2V (use the input image as the first frame / strict visual condition). It does not. Reading the upstream stock node body in `comfy_extras/nodes_wan.py:1070-1108`, `ref_image` is VAE-encoded into a soft `reference_latents` field appended to the positive conditioning, and the actual generation latent starts from zeros. HuMo is a face-locked audio-to-talking-head model: the reference is intended as a face-identity hint so the rendered character stays consistent across the clip. When the reference is a non-face image (we passed a 1940s broadcast-radio still rendered by FLUX), the identity attention has nothing to lock to, and HuMo defaults to text-prompt-driven face generation. With per-line seeds `(seed + idx*1009)`, two ANNOUNCER lines (l001 idx=0, l021 idx=20) rendered as two different generic blonde women, while the radio still that the ledger claims was used was completely ignored.

This breaks the architectural premise in `nodes/_otr_speaker_role.py:12-22` which declares "announcer → radio still, music_* → radio still, sfx → radio still — the radio is the visual performer for everything that isn't dialogue." HuMo physically cannot animate the radio. Wall-to-wall HuMo coverage is incompatible with the radio being the non-dialogue visual.

## The three fix candidates I'm considering

### Option 1 — ANNOUNCER becomes a cast member, radio still becomes a bookend mp4 (open/close interlude)
- Add an ANNOUNCER cast member in the LLM story-writer schema with a description like "1940s radio host at a vintage microphone, period-accurate suit, dim studio lighting."
- `BatchFluxRender` already produces cast portraits via `full_env_NNNNN_.png` — the announcer just becomes another cast entry, gets a portrait through the existing pipeline.
- `_otr_speaker_role.py` reroutes ANNOUNCER through the existing portrait chain (BUG-088 portrait resolver). Music_* and sfx routes also revisited — likely also become host portraits or fall through to "no clip" (audio-only segments concatenated as static frames in post).
- Radio still rendered exactly as today (one FLUX call with the dynamic prompt) but its only consumer is a 5-second static or slow-pan mp4 generated by ffmpeg, concatenated at episode open and close in `_render_master_mix_per_clip_mux_mode`. No HuMo in the loop for the radio.
- **Code change:** small. Mostly speaker_role rewiring + a `bookend_mp4` step in video_composite.
- **VRAM impact:** zero. Same model loadout.
- **Aesthetic:** matches OTR's "1940s radio drama" identity. Host at microphone, radio set in bookend interludes.
- **Risk:** if music_inter / sfx don't have a sensible cast portrait, those audio events have no visual companion → either they fall through to "extend previous clip," "freeze previous frame," or "static FLUX background pan."

### Option 2 — Two-pipeline split: HuMo for character only, LTX-2.3 (or static ffmpeg pan) for non-character
- Keep the existing premise that "radio is the performer for non-dialogue."
- For ANNOUNCER/music_*/sfx lines, route to a separate visual pipeline:
  - **LTX-2.3** (already in the v2 architecture under C4: 10-12 s clips, 257 frames @ 24fps, fp8_e4m3fn) animates the radio still with audio reactivity.
  - OR a static ffmpeg-driven Ken-Burns pan over the radio still (zero VRAM).
- HuMo strictly handles character dialogue.
- **Code change:** moderate. New node / branch in BatchHumoRender, LTX subprocess invocation in spawn context (per C3).
- **VRAM impact:** depends. LTX-2.3 loads ~8-10 GB; we'd need to free HuMo first. Sequential — one batch of HuMo character clips, free, one batch of LTX radio clips, free. Acceptable but adds wall-clock time.
- **Aesthetic:** preserves the "radio is the performer" idea Jeffrey originally wanted.
- **Risk:** LTX-2.3 output won't be lip-sync-aligned with audio (it's a generic motion model, not audio-driven). The radio "glitch-animates" but doesn't articulate to the audio rhythm — could feel like a screensaver overlaid on the audio. Static ffmpeg pan is the safer fallback.

### Option 3 — Hybrid: composite host-with-radio in the bookend FLUX render, feed THAT to HuMo
- FLUX renders an ANNOUNCER portrait that already includes the radio set in frame (vintage broadcaster sitting AT the radio console, microphone visible, console behind/beside).
- HuMo gets that composite as `ref_image`. Identity attention locks to the host's face. Radio appears in the rendered output as in-frame background scenery.
- ANNOUNCER lines produce video where you see a host speaking with the radio next to them — narratively reads as "the radio drama show."
- **Code change:** smallest. Just modify the dynamic radio bookend prompt in `visual/batch_flux_render.py:73-114` to render an ANNOUNCER+radio composite. No speaker_role rewiring.
- **VRAM impact:** zero.
- **Aesthetic:** keeps both — host speaks (HuMo does what it does well), radio is visible. Could feel cluttered or could feel period-perfect depending on prompt skill.
- **Risk:** prompt drift. FLUX may produce a host with radio one render, just a host the next, just a radio the next. Less visual consistency than Option 1 unless prompt is very tightly engineered.
