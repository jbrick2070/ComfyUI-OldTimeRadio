VERDICT: no. The plan is a high-level direction, not a build-ready spec. It lacks concrete steps for the descriptor builder, the render-side gate unification, and handling of non-input constraints (aspect ratio, creative fit) currently encoded in the roles whitelist. Without these, implementation will break existing routing or introduce inappropriate engine selections.

MUST-FIX BEFORE BUILD:
1. [Proposed direction / Hard question 1] The plan does not address constraints beyond input tokens (e.g., render_aspect="wide", creative appropriateness). Dropping the roles whitelist may allow engines to fit roles where they produce broken output (e.g., a wide-only engine in a portrait slot). **Fix:** Extend the capability model to include at least aspect ratio, or retain a separate aspect-compatibility check that does not rely on a per-engine role whitelist. Provide a concrete mechanism (e.g., engine declares `supported_aspects`, role declares `required_aspect`).
2. [Grounding – descriptor `roles` source] The plan says to drop the roles whitelist gate but does not specify how the director descriptor’s `roles` key is built or removed. The current code builds descriptors with a `roles` list; if left in place, other consumers may still read it and cause the same bug. **Fix:** Define exactly how `engine_fits_role` and the descriptor builder will change. Either remove the `roles` key entirely or derive it from `required_inputs` vs `ROLE_AVAILABLE_INPUTS` at build time. Specify the change in `otr_video_director.py`.
3. [Grounding – render_driver gate] The plan states “Single source -> both gates derive from it” but does not unify `FAMILY_REQUIRED_INPUTS` with the engine’s `required_inputs`. The render-side gate currently uses a separate mapping; if it stays, capability declarations are not truly single-source. **Fix:** Derive `FAMILY_REQUIRED_INPUTS` from the engine’s `required_inputs` (or from a shared capability registry) so that the render-time check matches the selection-time check. Provide the code change for `_assert_family_inputs_satisfiable`.
4. [Invariants] The strict-superset invariant is asserted but not proven. The plan asks for a per-engine × per-role BEFORE/AFTER table; without it, regression cannot be verified. **Fix:** Produce the table as part of the design, enumerating all current engine–role pairs and confirming that every existing fit remains, and that only additive changes occur.
5. [Hard question 1 / default_roles] The plan notes `default_roles` is a separate concern but does not clarify how auto-default selection will work after the whitelist is removed. If `default_roles` is still used to pick a default engine for a slot, the logic must be adapted to the new capability-only world. **Fix:** Specify whether `default_roles` will be dropped, derived from capabilities, or kept as an explicit hint. If kept, ensure it does not conflict with the capability gate.
6. [Goal – image engines] The plan says “Extends to IMAGE engines too” but provides zero detail on image engine capability declarations or how they integrate. Without that, the implementation will be incomplete. **Fix:** Include image engine capability model and routing changes in the design, or explicitly scope this phase to video engines only and defer image engines.

SHOULD-FIX:
1. [Proposed direction] The subset condition “consumed inputs ⊆ role’s available inputs” does not handle engines with optional inputs. If an engine can use `init_image` if present but does not require it, the current `required_inputs` tuple would omit it, making the engine eligible for roles that lack `init_image`, which may be desired. **Fix:** Add an `optional_inputs` field to engine declarations and adjust the fit condition to require all `required_inputs` present and allow `optional_inputs` to be absent.
2. [Migration] The plan should include a step to remove the `roles` attribute from all engine definitions (if it exists) and ensure `required_inputs` accurately reflects all consumed inputs. This prevents stale data.
3. [Safety] With the whitelist gone, the engine pool for each role may grow significantly. The director’s selection logic (e.g., random choice, priority) may need tuning to avoid picking a technically compatible but creatively poor engine (e.g., a still-image engine for a video slot). **Fix:** Document how the director will choose among multiple eligible engines, and consider a priority or scoring mechanism that does not rely on a hardcoded role list.

OPTIONAL / NICE-TO-HAVE:
- Provide a unified `Capability` dataclass that includes input tokens, output modality, aspect constraints, etc., and generate both the selection gate and the render-side check from it. This would make the single-source-of-truth explicit and testable.

CUT THESE (over-engineering):
- None. The document is a problem statement, not an over-engineered design. The proposed direction is minimal.
