# TRANSPLANT PLAN -- lab lessons into OTR, lane by lane

Date: 2026-08-09. Companion to `2026-08-09-SPEC-lab-findings-into-otr.md`.
The spec is organised by CHANGE (S1-S10). This document is the same work
organised by LANE, so the question "is every video path named right and
working right?" has one place to be answered.

Read this with the spec open: the spec carries the reasoning and the
file:line evidence; this carries the per-lane checklist and the finish line.

**Definition of "working right" used below** (a lane must clear all five):
1. It STARTS -- weights resolve on this box, preflight passes, boot lane exists.
2. Its CANVAS is declared, /32-legal, and matches what the graph renders.
3. Its FRAME CONTRACT matches what it actually emits, at the canvas rate.
4. It REFUSES rather than OOMs -- admission is enforced or honestly reported
   as unenforced.
5. Its AUDIO is proved silent on its own emitted file (V-1), not merely
   declared.

**Naming:** `<model><version>_<low|high>_<capability>`. `low` = measured under
~8 GiB, `high` = 12 GiB+. Internal ids NEVER rename; every current public id
stays registered as an alias so saved graphs resolve.

## Clip-window maths and still consumption, per lane

The two are coupled: continuity decides the join mode, and the join mode
decides how many stills a beat eats. CHAIN lanes inherit the previous
segment's terminal frame (scene still for segment 0 only); JUMP lanes mint a
FRESH still per segment (the still spine + image dispatcher must keep up);
SINGLE lanes never chain. All seconds at the 25 fps canvas rate. Example
segment counts for a 30 s (750-frame) beat are ILLUSTRATIVE - the r3 rule
stands: pin exact partition literals by running the real `partition_beat`,
never by hand.

Build consequences this table forces:
1. **Jump-still budgeting.** A long hero beat on 14B costs ~1 still per 3.9 s

   lane's cost, and the acceptance episode must include at least one
   multi-segment JUMP beat to prove the minting keeps up.

## Order of operations -- ONE LANE AT A TIME (operator ruling 2026-08-09)

"Build one lane at a time and test it, then move to the next, so a bug we hit
on one gets PREVENTED on the next." That is the build law for this campaign.
It beats a change-ordered sweep because these lanes share failure shapes:
weight resolution, canvas declaration, contract-vs-runtime drift, receipt
completeness. Each finished lane converts a bug into a checklist item the next
lane never pays for.

### The lessons ledger (the mechanism that makes this work)

Maintain `docs/LANE_BUILD_LESSONS.md`. After EVERY lane closes, append what
actually bit -- symptom, root cause, the check that would have caught it. Then
the NEXT lane starts by running that whole ledger against itself BEFORE any
code is written. A lesson is not recorded until it is phrased as a check
someone can run.

Seed the ledger with the four already known from the 2026-08-09 audits, so
lane 1 starts with a real checklist rather than an empty file:
- **L1 Weight resolution:** does the lane resolve its weights through
  `folder_paths`, or does it hardcode a path that happens to be wrong on this
  box? (wan_i2v: hardcoded, lane dead.)
- **L2 Canvas truth:** does it DECLARE `render_canvas`, is it /32-legal, and
  does it match what the graph actually renders? (humo_14B_169: 3.07x
  disagreement. Nine lanes: profile canvas read by nobody.)
- **L3 Contract vs runtime:** does the declared frame contract match what the
  adapter emits, AT THE CANVAS RATE? (H3: 24 vs 25 fps. ltx_video: renders 169
  regardless of the ask.)
- **L4 Receipt completeness:** does the clip dict carry `vram_peak_mb`,
  `recipe`, `render_canvas`, and is silence PROVED on the emitted file rather
  than declared? (HuMo: nulls. Every adapter: `has_audio` is a literal.)

### Per-lane loop (run this for every lane, no exceptions)

1. Read `LANE_BUILD_LESSONS.md` top to bottom; check THIS lane against every
   entry before writing code, and note which ones it already fails.
2. Run `tests/test_lane_preflight_matrix.py` (spec S8c) and record THIS
   lane's failing rows -- that IS the lane's work list, before any code.
3. Code the lane.
4. Wire it (profile, boot contract, node-87 if the dropdown changed).
5. Regress: AST parse, dead-ref grep, cross-import check, widget count vs
   `widgets_values`, full Windows suite, Bug Bible.
6. PREFLIGHT GATE: the lane's preflight-matrix row flips GREEN -- weights,
   canvas, contract, admission honesty, V-1 self-probe, guards, surface.
   A lane whose row is red does not smoke, does not commit, does not count.
7. Smoke the lane ALONE -- one real render proving the row's claims live.
8. Commit and push the chunk.
9. Append what bit you to `LANE_BUILD_LESSONS.md`, phrased as a runnable
   check (new checks get ADDED to the preflight suite, so later lanes pay
   nothing to inherit them). If nothing bit, write that too.
