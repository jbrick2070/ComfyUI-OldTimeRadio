- id: "12.103"
  phase: 12
  area: a-model-rewrite-pass-must-never-hold-authority-over-a-field-another-owner-writes-deterministically
  symptom: |
    A voiced/spoken row ships shorter than what was composed -- a deterministic,
    Python-owned fact appended verbatim by an earlier assembly step is silently
    gone from the final row, even though the interpreter that produced the fact
    was correct and the ledger still carries the original sentence elsewhere in
    meta. Measured: a closing-announcer row that should read an authored bridge
    plus a factual news coda shipped with only the bridge; the durable meta
    fields that hold the true sentence (spoken_coda_source/provenance_coda_line)
    still carry it, so the RECEIPT and the SPOKEN ROW disagree. Rewrite rate
    measured at 9 of 14 voiced rows across three episodes in one overnight gate.
  cause: |
    A later cleanup/"clean stage" pass judges every voiced row for "anything
    that is not speech" and hands a MODEL the rewrite of what it flags. The pass
    has no concept of a protected/content-owned span within a row -- it treats
    the row as one undifferentiated block of text to judge and rewrite, not as
    a composite of an LLM-authored bridge plus a Python-appended fact. Whatever
    the model decides is "not speech" (or simply drops during rewrite) is gone,
    and nothing downstream distinguishes "the model paraphrased this" from "the
    model deleted this." It shipped unnoticed because the pass was proven safe
    on a planted-ledger measurement rig that never runs the writer tail and
    therefore never composes a coda -- the one row shape with a protected
    component was never in the harness's input space.
  fix: |
    Mark protected/content-owned spans at the point of composition -- the same
    call that appends the deterministic fact records the exact appended
    substring, not just the finished row -- and make the clean/rewrite pass
    read that mark BEFORE it ever hands a row to the model: rows carrying a
    protected span are either excluded from full-row model rewrite, or the
    rewrite is scoped to operate only on the non-protected portion and the
    protected substring is re-appended byte-identically afterward.
    DO NOT "fix" it by asking the model nicely to preserve facts in the prompt
    -- an instructed model is still a model, and the guarantee must be
    structural (the protected span physically cannot enter the model's edit
    surface), not persuasive.
    DO NOT fix it with a post-hoc check that only logs a warning -- the row
    must ship correct, not merely diagnosed as wrong after the fact.
  verify: |
    (1) For any ledger whose meta carries a Python-owned coda/fact value,
    assert that value appears byte-identically at least once in the
    corresponding final row's text -- anchor on the durable meta value with a
    substring/endswith test, never on a fixed separator string, since the
    separator itself is conditional on other flags.
    (2) Feed the clean stage a synthetic row built from a bridge + protected
    coda, same shape as production, and assert the protected substring
    survives rewrite untouched while the bridge may still be modified.
    (3) Close the fixture gap directly: extend whatever measurement rig proved
    the clean stage safe so its planted ledgers include at least one row
    carrying a protected span -- the original miss was a rig that could not
    have caught this by construction.
    (4) Re-run the real writer tail on a live leg and diff the receipt's
    recorded coda source against the shipped row's text.

    positive; the snapshot must learn about the mutator, or move past it, not
    stop looking carefully.

  symptom: |
    A bounded repair/retry ladder exhausts all attempts re-emitting the SAME
    malformed token/output, even though the ladder mechanically does carry the
    rejected draft plus its defect list into the next turn. Measured: a
    terminal-delimiter parser required a literal `END.` (with period); the
    model wrote bare `END` on every rung across four attempts, because the two
    reported defects (a bad line shape, a missing terminal marker) describe
    what is wrong with zero indication of the one-character fix that would
    satisfy them.
  cause: |
    The defect/diagnostic text a repair turn receives states the OFFENSE
    ("this line's shape is bad", "the terminal marker is missing") but never
    states the REQUIRED SHAPE (the exact accepted string or pattern). A model
    has no way to infer "add a period" from being told its output is malformed
    and missing -- those are two symptoms of one omission, not two independent
    facts it can reason its way out of. Because the repair mechanism (carrying
    the rejected draft plus defects forward) LOOKS complete -- it does feed
    context forward -- the missing ingredient (the target) is easy to miss in
    review; the ladder's plumbing is not the defect, its payload is.
  fix: |
    Every defect a repair loop reports must carry, alongside what is wrong, a
    positive statement of what would be accepted -- the exact required
    literal, an example of the accepted shape, or a regex/grammar description
    a small model can pattern-match against. Where the accepted set is small
    (a fixed terminal delimiter, a fixed enum), show the literal value
    directly in the defect text, not merely the pattern that validates it.
    Audit every OTHER repair-loop defect type in the same module family for
    the same omission -- a diagnostic that shipped naming the offense without
    the target is a defect CLASS, not a one-off, and the fix belongs at the
    shared defect-construction site so a new defect type inherits it rather
    than needing the lesson relearned per call site.
  verify: |
    (1) For every accepted terminal/delimiter form the parser recognizes,
    assert exactly one canonical form and require the repair-turn defect text
    to contain that literal string verbatim.
    (2) Construct a fixture whose only defect is the ONE-CHARACTER gap (bare
    `END` vs `END.`) and assert the repair ladder converges within its normal
    budget once the defect text names the required literal -- this is the
    regression that matters, it is exactly the input that exhausted the ladder
    live.
    (3) Statically scan every defect-construction call site feeding a repair
    prompt and assert each includes a "required"/"expected" field alongside
    the "offense"/"reason" field -- a structural check that catches the next
    diagnostic authored the old way.
    (4) Content-bearing and unpaired-bracket variants must still fail loud --
    the fix must not turn the validator permissive.
  tags: [repair-loop, retry-ladder, diagnostic-design, required-shape, unrepairable-by-construction, markup-parser, defect-class-sweep, xref-11.26, xref-11.35]

- id: "12.108"
  phase: 12
  area: a-live-feed-consumed-by-a-constant-index-retells-the-newest-item-forever
  symptom: |
    A lane that adapts from a live, ordered feed (newest-first) produces the
    SAME underlying source on every run absent explicit operator intervention
    -- and there is no code path, test, or log that would ever reveal this,
    because each individual run looks correct in isolation (it successfully
    adapts a real, current feed item).
  cause: |
    Item selection reads a configured index into the feed's payload list, and
    that index defaults to a constant (`0`) when no operator override is set.
    Because the feed arrives newest-first, index 0 IS the newest item on every
    single invocation -- there is no history, dedup, or rotation state
    anywhere in the selection module, so "always pick the newest" and "pick a
    fresh item each time" are indistinguishable from a single run's log, and
    only comparing multiple runs' selected headlines reveals the defect. The
    selection path has no test at all, so nothing exercises it across more
    than one invocation.
  fix: |
    Selection must carry state ACROSS runs for any lane whose source is a
    live, changing feed: record the identity (headline/url/id) of the item
    selected each run in durable storage, and have the next run exclude
    recently-used items (or otherwise rotate/rank rather than reading a
    constant offset). A constant-default index is only safe for a feed the
    operator is expected to pin deliberately; where the intent is variety, the
    default must be "pick something not recently used," not "pick position
    zero." Additionally, stamp the selected item's own headline into durable
    meta at SELECTION time (not reconstructed later from today's fetch),
    since "which post did this episode adapt" cannot be answered after the
    fact from a feed that has since moved on.
  verify: |
    (1) Run selection twice in immediate succession against a stable/replayed
    feed fixture and assert the two runs select DIFFERENT items whenever more
    than one eligible item exists.
    (2) Assert the selected item's headline is present in the episode's
    durable meta after a run, sourced from selection time, not re-derived
    later.
    (3) Statically: grep-confirm the selection module has at least one test
    exercising more than a single invocation -- the admission finding here was
    precisely that no test existed at all.
    (4) With only one eligible item in the feed, assert selection still
    succeeds (falls back to the single item) rather than treating exhaustion
    as an error.
  tags: [live-feed, constant-index, no-rotation, no-dedup, selection-state, durable-receipt, rss, media-archive, untested-path]

- id: "12.109"
  phase: 12
  area: a-renamed-entitys-derived-text-keeps-the-old-name
  symptom: |
    A single catalog/cast record disagrees with itself: its canonical identity
    field names one entity, while OTHER fields on the SAME record -- free-text
    fields an earlier LLM pass authored FROM the identity, such as a character
    description and a speech-signature -- name a DIFFERENT entity throughout.
    Measured: `name: "TARIQ SCOTT"`, `character_description` reading
    "...HENRY BARTEL, Seasoned Craftsman...", `speech_signature` reading
    "Henry's sentences often begin with a pause...". A sibling record in the
    same cast shows no such disagreement, so the fault is a per-row desync,
    not a lane-wide defect.
  cause: |
    A record's canonical name field and its LLM-derived free-text fields
    (description, speech signature) are populated at different times from the
    same identity, and nothing re-derives or invalidates the free-text fields
    when the canonical name changes after they were authored. The description
    LLM, the portrait prompt, the dialogue cast block, and the image prompt's
    gender anchor all read the record as a single coherent identity and have
    no way to detect that two of its fields were authored against a name the
    record no longer carries -- each individually-read field looks
    well-formed, so no single consumer's own validation catches the
    cross-field disagreement.
  fix: |
    Treat a character record's identity-derived fields as a set that must be
    regenerated -- not merely left stale -- whenever the canonical identity
    field they were derived from changes; the rename and the re-derivation are
    one transaction, the same discipline as clearing a paired flag in the same
    mutation that changes its partner. Where full regeneration is not
    immediate, at minimum invalidate (null, not silently keep) the derived
    fields on rename so a downstream reader gets an obvious gap instead of a
    confidently wrong cross-reference. Add a same-record cross-field identity
    invariant that runs before a record is allowed to feed any downstream
    prompt: canonical name, description subject, speech-signature subject,
    caption identity, and voice mapping must all name the same entity.
  verify: |
    (1) A record-level invariant check, run over every cast record before
    rendering, that greps each derived free-text field for any OTHER cast
    member's full name and fails if found -- automatable and requires no
    semantic understanding, since a full-name string match on a closed cast
    roster is a hard fact.
    (2) Construct a fixture that renames a record after its derived fields
    were authored and assert the invariant catches the resulting disagreement
    pre-fix and passes post-fix.
    (3) Confirm the sibling-record negative case: an untouched record with
    self-consistent fields must not trip the invariant, so the check does not
    merely flag everything.
    (4) Re-run the invariant against the live episode that shipped the defect
    and confirm it now fails loudly where it previously shipped silently.
  tags: [renamed-entity, derived-text, stale-description, identity-drift, cross-field-invariant, cast-record, speech-signature, per-row-desync]
