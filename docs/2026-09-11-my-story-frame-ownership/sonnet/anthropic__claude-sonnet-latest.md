## Findings

**1. Structural gap: only cast *names* are validated; leaked frame narration in prose is not (nodes/_otr_my_story.py:503, `_make_treatment_validator`).**
The reserved-name check only inspects `model.names()`. If the model removes "ANNOUNCER" from the `cast` array but still writes house-frame content into `acts[i].turns` or `ending` (e.g. "The announcer welcomes everyone" without the literal cast name), the post-validator never fires, so the typed-repair path in `_full_artifact_repair` is never invoked. The only remaining backstop is the optional, LLM-driven `source_rewrite_instruction` passed in `_pass_treatment`, which is not deterministic and depends on `source_rewrite_receipts` being supplied by the caller at all. `actual08` diagnosis explicitly showed frame leakage independent of the reserved cast slot ("both complete P1 drafts include ... an ANNOUNCER opening" while cast already carried Jeffrey/Mother), so this is precisely the failure mode the diff is meant to close, but the fix only catches it when the model also puts "ANNOUNCER" literally in `cast`. The Bible entry explicitly rules out prose-scanning as a remedy, so this is a known, accepted residual gap — but the QA claim that "the same reserved cast error condition now gives conditional whole-treatment action" should be read narrowly: it is conditioned on the reserved-name being *in cast*, not on frame leakage occurring at all.

**2. P0 (`_pass_interpret`) carries no structural enforcement at all (nodes/_otr_my_story.py:463-483).**
Unlike the treatment pass, `_pass_interpret` has no `post_validator`. The frame-ownership rule for `named_cast`/`cast_plan` is entirely prompt-text (system prompt + `source_rewrite_instruction`). This is stated to be "by design" (no semantic post-validator for P0), but it means the whole P0 half of the fix is unverifiable by any mechanism other than the LLM's own compliance and, once, the P0-source correction call. `actual08` showed a real production model (Gemma) putting Announcer in `named_cast` as `required`; nothing in this diff structurally prevents recurrence at P0, it only asks more clearly. That's consistent with the stated non-goal, but worth flagging since it's the exact failure this round targeted.

**3. Redundant/tripled instruction surface increases prompt size on every call.**
The same frame-ownership rule now appears in: the static system prompt (my_story.json, both `interpret` and `treatment` stages), the dynamic `source_kwargs["source_rewrite_instruction"]` set unconditionally in `_pass_interpret`/`_pass_treatment`, and the validator's repair message text. All three are sent together in the repair round (system + repair instruction + validator error), plus the raw source block prepended by `_call`. This isn't functionally wrong but is duplicative token overhead on every treatment call (not just failures, since `source_rewrite_instruction` is always set), which works against context-budget headroom noted as a concern in `actual08` ("2178 tokens... fits=true" was already a near-miss data point for a short one-act story). No token-budget analysis is offered for longer/multi-act sources.

**4. Unconditional overwrite of `source_kwargs["source_rewrite_instruction"]` (nodes/_otr_my_story.py:467, 532).**
Both passes unconditionally set this key in the *local* `source_kwargs` dict, discarding anything a caller might have wanted to pass. The test `test_p0_p1_scope_stays_local_and_reaches_existing_source_owner` confirms the caller's original dict is untouched (kwargs-copy semantics protect the caller), but there is no mechanism for a caller to *extend or compose* an instruction rather than being silently overridden — if a future feature needs to add an orthogonal source-rewrite instruction to these two passes, this diff's pattern will silently clobber it. Minor design smell, not a current bug, but worth naming since it's now duplicated in two call sites and will need to be duplicated again for any future third instruction.

**5. Combined problem message ordering/format is implicit contract, not enforced by type.**
`_make_treatment_validator` now builds `problems` as a list joined with `"; "` and returns `None` if empty. The repair-prompt test asserts substring presence/ordering (`"exactly %d acts"` and the reserved-name text both present when both fire), but there's no test for the case where *only* the act-count problem fires (former behavior, unchanged) still produces a sane message on its own — presumably fine since it predates this diff, just flagging it wasn't re-verified here for the combined-message change specifically beyond the parametrized case.

**6. Test evidence explicitly disclaims semantic quality — appropriately.**
The new tests (`test_treatment_frame_repair_replaces_owned_fields_in_the_saved_ledger`, etc.) use scripted/canned model responses to prove wiring (prompt reaches the right call, repair prompt contains the right substrings, saved ledger reflects the fixed payload). This is correctly scoped and honestly labeled ("Canned returns prove repair delivery/application, not model fidelity"). No objection here — just noting the plan's claim that "actual08 evidence grounds this failure" is not itself re-validated by a live model in this diff; that's deferred to the promised canonical run, which is fine as stated.

## Not reopened
No objection to: absence of a new semantic gate, absence of fuzzy/alias matching, the 2-call P1 source-rewrite budget, or the shared-repair mechanism itself — these match the stated settled constraints and I see no new code evidence to contradict them.

## Verdict
