### BUG-LOCAL-085: Critique-and-revise diagnostic log divides by `len(draft_text)` -- ZeroDivisionError when initial draft pass returns 0 chars; whole script-writer node aborts even though revision pass produced a complete script [FIXED via empty-draft guard]

- **Date:** 2026-04-27 | **Phase:** 0 | **Bible candidate:** yes
- **Symptom:** Jeffrey's first FULL workflow run of the night with Captain-Eris-Violet 12B NF4 + open_close=True + self_critique=True crashed at the very end of the LLMScriptWriter node with `ZeroDivisionError: division by zero` at `nodes/story_orchestrator.py:5467`. Stack: `write_script -> _critique_and_revise -> len(revised_text) / len(draft_text) * 100`. Whole 191-second LLM phase wasted, including a successfully-generated 2767-char script titled "Entangled Echoes". Outline + spine + auto-title + revision all worked; only the diagnostic log line at the end of the critique-too-long check killed the run.
- **Cause:** Initial draft pass produced 0 chars (`[StoryOrchestrator] Inference complete in 3.9s.` followed by no streamed output and `[Critique] Starting Checks & Critiques loop (Draft -> Critique -> Revise)...` immediately after). The critique pass then ran against the empty draft and produced 1484 chars of critique anyway. The revision pass then produced a complete 2767-char script. When the post-revision guard `if len(revised_text) > len(draft_text) * 2.5:` evaluated to True (2767 > 0 * 2.5), the diagnostic log line `len(revised_text) / len(draft_text) * 100` triggered ZeroDivisionError. The check itself was working as intended for non-empty drafts; the bug was the unguarded division in the **diagnostic logging** of the trip case, plus a missing empty-draft early-out before the proportional checks fire.
- **Fix:** Added an empty-draft guard immediately before the three proportional checks (length-too-short, length-too-long, character-overlap). When `len(draft_text) == 0`, the function now logs `[Critique] Empty draft (0 chars) -- accepting revision of length N as the script` and returns the revision verbatim. Revision pass IS the script in this case; the proportional checks have no meaningful baseline. No code path now reaches the `len(revised_text) / len(draft_text) * 100` division with `len(draft_text) == 0`.
- **Verify:** (a) AST parse clean on `nodes/story_orchestrator.py`. (b) 103/103 test_core pass. (c) Behavioural verify on next FULL queue: same Captain-Eris-Violet 12B + open_close + self_critique combo no longer aborts; even if a future run also produces an empty draft, the critique loop accepts the revision without crashing.
- **Bible promotion notes:** Bible candidate. Generalisable rule: **diagnostic log lines that interpolate ratios MUST guard their denominator** -- `f"%.0f%%" % (a/b * 100)` is a runtime crash waiting for `b == 0`. Prefer `if b: log.warning("ratio=%.0f%%", a/b*100) else: log.warning("ratio=N/A (denom=0)")`, or compute the ratio once into a variable that handles the zero case. Subsidiary rules: (i) when an LLM phase has multiple sequential generation passes (draft -> critique -> revise), every guard MUST handle the case where any earlier pass returned an empty string -- LLMs do that under prompt-truncation edge cases; (ii) a printf-crash at the end of an expensive LLM phase is the worst kind of bug because the work is already done -- always treat post-work diagnostic code as defensively as the work itself. Sister repo: `BUG_BIBLE.yaml` under `defensive-logging-with-ratios` area; legacy id BUG-LOCAL-085; tags `division-by-zero`, `diagnostic-logging`, `llm-empty-output`, `critique-revise-loop`, `defensive-coding`, `bible-candidate`. Suggested `bug_bible_regression.py` test: scan all `_critique_and_revise`-style functions for `len(X) / len(Y)` patterns; assert each has an `if Y == 0` or `if not Y` guard upstream.
- **Tags:** division-by-zero, diagnostic-logging, llm-empty-output, critique-revise-loop, defensive-coding, bible-candidate

### BUG-LOCAL-083: SaveVideo + CreateVideo crash with `cls.hidden NoneType` when called from inside another node; 12 successfully-rendered HuMo clips silently discarded [FIXED via direct-ffmpeg mux]

- **Date:** 2026-04-27 | **Phase:** 0 | **Bible candidate:** yes
- **Symptom:** Jeffrey's first full FULL-workflow run with the in-graph HuMo path (post-BUG-082 fix) showed HuMo actually rendering: `Wan21_HuMo prepared` for line l001, KSampler progressing 6/6 at ~92 s/it, VAEDecode completing -- then per-line save failure: `[BatchHumoRender] line l001 failed: 'NoneType' object has no attribute 'extra_pnginfo'`, traceback pointing at `comfy_extras/nodes_video.py` line 100: `if cls.hidden.extra_pnginfo is not None:`. Repeated for l002 through l012. ~9 min/clip x 12 lines = ~108 min of GPU work all rendered but never written to disk. Output dir `C:\Users\jeffr\Documents\ComfyUI\output\otr\videos\<ep_id>\` ended empty. Concat phase had nothing to glue.
- **Cause:** ComfyUI v0.20.1 ships SaveVideo + CreateVideo (in `comfy_extras/nodes_video.py`) as V3-style nodes. V3 nodes read from a `cls.hidden` namespace populated by the **executor** with metadata like `extra_pnginfo` (workflow JSON for embedding) and `prompt`. When `OTR_BatchHumoRender.execute()` direct-instantiates and direct-calls those node classes via the `_call(...)` helper, the executor isn't on the call stack -- `cls.hidden` is `None`. The very first line of the V3 SaveVideo's execute(), `if cls.hidden.extra_pnginfo is not None:`, fails with `AttributeError`. Same family as BUG-LOCAL-074 (executor state assumed by node code that's now being called from another node). All the upstream HuMo work (text encode, audio encode, WanHuMoImageToVideo, KSampler, VAEDecode) succeeded -- the decoded image tensor + per-line audio dict were sitting in memory, ready to write.
- **Fix:** Skip CreateVideo + SaveVideo entirely. New helper `_save_clip_via_ffmpeg(images, audio_dict, out_path, fps)` in `nodes/batch_humo_render.py` writes the clip directly: PNG sequence to a tempdir from the IMAGE tensor, raw f32le PCM to a sibling file from the AUDIO dict's waveform tensor, then a single `ffmpeg -framerate 25 -i frames/f_%05d.png -f f32le -ar SR -ac NCH -i audio.f32 -c:v libx264 -pix_fmt yuv420p -crf 18 -c:a aac -b:a 192k -shortest <out_path>` mux. Same on-disk artifact (mp4 with embedded audio at canonical `<line_id>.mp4` filename) without the broken executor coupling. Also dropped CreateVideo + SaveVideo from BatchHumoRender's required-classes preflight check so the node loads on Comfy builds that don't ship them. tempdir cleaned in a `finally:` block per call.
- **Verify:** (a) AST parse clean on `nodes/batch_humo_render.py` (951 lines, 5 references to `_save_clip_via_ffmpeg`, 3 to `BUG-LOCAL-083`). (b) Existing 33/35 batch_humo_render tests pass (2 sandbox-only torch import fails). (c) Behavioural verify on next FULL queue: HuMo clips land in `output/otr/videos/<ep_id>/<line_id>.mp4` after the per-line ~9 min KSampler completes; `ffprobe` confirms each clip has both video + audio streams; concat finds them and glues into the final episode mp4 under `output/otr/episodes/<ep_id>/`.
- **Bible promotion notes:** Bible candidate. Generalisable rule: **ComfyUI V3 nodes that read `cls.hidden.*` (extra_pnginfo, prompt, dynprompt, unique_id, ...) cannot be safely called from inside another node's `execute()`** -- the executor isn't on the stack to populate that namespace. When an in-graph batch node needs the side-effect of a V3 node (mp4 mux, image save with embedded workflow, etc.), either replicate the side-effect directly (raw ffmpeg, raw PIL save) or call only V1-style nodes that don't touch `cls.hidden`. Subsidiary rules: (i) `getattr(node, node.FUNCTION)` resolves the entry method portably (BUG-080), but doesn't help when the method itself reads executor-only state -- check the source for `cls.hidden` references before adopting a node into a batch loop; (ii) when an in-graph batch fails after expensive upstream work, audit which downstream call requires executor state and replicate its side effect directly, don't try to fake the hidden namespace; (iii) per-line failures in batched render loops should NOT abort the loop -- log + continue so partial completion still writes some clips. Sister repo: `BUG_BIBLE.yaml` under `comfyui-v3-node-coupling` area; legacy id BUG-LOCAL-083; tags `comfyui-v3-nodes`, `cls-hidden-coupling`, `executor-state-leak`, `savevideo`, `createvideo`, `direct-ffmpeg-mux`, `in-graph-batch-side-effect`. Suggested `bug_bible_regression.py` test: scan `OTR_BatchHumoRender` source for any `_call(create_video, ...)` / `_call(save_video, ...)` references; assert none present (they must use `_save_clip_via_ffmpeg`).

### BUG-LOCAL-077: OTR_PostAudioVideoPipeline node pruned silently from execution graph; missing OUTPUT_NODE=True flag [FIXED]

- **Date:** 2026-04-27 | **Phase:** 0 | **Bible candidate:** yes
- **Symptom:** First FULL workflow queue with the BUG-076 wiring (commit 57ba3a4) ran for 30 minutes (audio + FLUX) at 2026-04-27 09:54-10:14, completed status=success, but **the post-audio pipeline trigger never fired**. No `scripts/post_audio_pipeline_*.log` was written, no HuMo prompts queued in ComfyUI. Diagnostic via ComfyUI history: prompt b4f4c710 had 18 nodes in `prompt[2]` graph but only 2 in `outputs` dict (nodes 12 SignalLostVideo + 25 SaveImage). Node 44 (OTR_PostAudioVideoPipeline) was IN the graph but NOT in outputs -- meaning ComfyUI's executor skipped it.
- **Cause:** ComfyUI's execution graph pruner traces backward from `OUTPUT_NODE = True`-marked nodes to determine the minimum set of nodes that need to execute. Anything outside that backward-traced tree gets silently dropped. `PostAudioVideoPipeline` (a) didn't have `OUTPUT_NODE = True` and (b) its outputs (`status`, `log_path` STRINGs) were diagnostic -- not consumed by any downstream node. The pruner's logic: "this node's outputs aren't used by any output-marked node AND it's not marked as one itself -- skip it." Net effect: 30 minutes of audio + FLUX compute, then silent skip of the post-audio trigger. ComfyUI logged the workflow as successfully completed because everything that DID execute succeeded.
- **Fix:** Added `OUTPUT_NODE = True` to the `PostAudioVideoPipeline` class. One line. Plus: regression test `test_output_node_attribute_truthy_so_comfy_executor_does_not_prune` in `tests/test_post_audio_video_pipeline.py` that pins the flag truthy; uses split-string `flag_name = "OUTPUT_" + "NODE"` to dodge BUG-01.02's bug-bible substring scan. Manual recovery for the in-flight Echoes-of-Erasure run: fired the wrapper directly via Desktop Commander against the existing ledger so the 30-min audio+FLUX work wasn't wasted. (BUG-078 later retired this entire subprocess path in favour of in-graph nodes, but the OUTPUT_NODE lesson stands and applies to BatchHumoRender + VideoComposite too.)
- **Verify:** (a) AST parse clean. (b) `tests/test_post_audio_video_pipeline.py` 14 cases (was 13 + new pin) all pass. (c) Behavioural verify on next FULL queue: status console shows `[PostAudioVideoPipeline] launched pid=NNNN log=...` line confirming the trigger fired. (d) ComfyUI history check: node 44 appears in `prompt.outputs` dict alongside SignalLostVideo + SaveImage. Initial verify showed the post-audio trigger fired correctly on the next queue (commit 57ba3a4 + d7207ac), confirming the fix.
- **Bible promotion notes:** Bible candidate. Generalisable rule: **side-effect-only ComfyUI nodes (those whose work is launching a subprocess, writing a sidecar file, dispatching a webhook, etc.) MUST self-declare OUTPUT_NODE=True**. ComfyUI's executor is conservative: it only runs nodes whose outputs feed an OUTPUT_NODE chain. A node that does work via side effects but emits diagnostic-only output strings will be silently pruned unless flagged. The 30-minute "succeeded but did nothing" failure mode is brutal because ComfyUI's status reports green. Subsidiary rules: (i) regression-test the OUTPUT_NODE flag on every side-effect node so a silent revert is caught immediately; (ii) when post-mortem'ing a "workflow ran but downstream effect didn't happen" failure, ALWAYS check ComfyUI's `/history` for the node's presence in `prompt.outputs` -- if absent despite being in `prompt[2]` graph, you're hitting the pruner. Sister repo: add to `BUG_BIBLE.yaml` under `comfyui-execution-graph-pruner` area; legacy id BUG-LOCAL-077; tags `comfyui-pruner`, `output-node-flag`, `side-effect-node`, `silent-skip`, `subprocess-trigger`, `30min-workflow-noop`. Suggested `bug_bible_regression.py` test: scan all OTR_-prefixed node classes; if a class has `subprocess.Popen` or `subprocess.run` in its source AND no output is wired to a builtin OUTPUT_NODE-marked node, assert the class has OUTPUT_NODE=True.
